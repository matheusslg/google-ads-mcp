## Context

`google-ads-mcp` is a Python ≥ 3.11 MCP server distributed via `uvx`, exposing the Google Ads API to AI agents through workflow-shaped tools with built-in safety rails. Issue #1 is the bootstrap: a runnable empty shell with a `ping` no-op tool, MIT license, and a README skeleton. The full v0.1.0 release (#7) layers real Google Ads tools (issues #4–#6), OAuth (#3), and test-account validation on top of this scaffold.

This spec exists so that the implementing agent (and any future contributor) has a single document explaining *why the scaffold is shaped this way* before reading the code.

## Reference Implementation Note

The PRD calls out `matheusslg/google-search-console-mcp` as the "same playbook". Investigation confirmed that repo is **TypeScript/Node**, not Python — so it informs **project shape and philosophy** (MIT, OSS, minimal README focused on install + Claude Desktop config + first-call example, no marketing fluff) but **not** the Python-specific scaffolding choices below. Those follow current Python ecosystem conventions (PEP 621, PEP 639, PEP 735) and the `uv` blessed path.

## Decisions

Four design questions were resolved during brainstorming:

| # | Question | Choice | Rationale |
|---|---|---|---|
| 1 | Layout | **src-layout** | Industry default for modern Python packages; forces editable installs to behave like real installs and catches missing `__init__.py` / `import-from-cwd` bugs early. |
| 2 | Bootstrap | **`uv init --package`** | Packaged project with hatchling backend, `[project.scripts]` block, src-layout — uvx-ready out of the box. Stays inside uv's blessed path. |
| 3 | Day-1 server shape | **Single `server.py` with `ping` tool** | Matches issue #1's literal requirement ("a no-op tool for connectivity check"). The modular file layout in `standards.md` is the *target state*, not day-1 state. Split occurs naturally as #4 onward add content. |
| 4 | OAuth helper | **Defer entirely to issue #3** | Issue #1's acceptance criteria don't mention auth; pre-stubbing the entry point now would create cross-issue scope creep. #3 will add both the function and the `[project.scripts]` line in one PR. |

## Code

### `src/google_ads_mcp/__init__.py`

```python
"""google-ads-mcp — MCP server for Google Ads workflows."""

from importlib.metadata import version

from google_ads_mcp.server import main

__version__ = version("google-ads-mcp")

__all__ = ["main", "__version__"]
```

Single source of truth for the version is `pyproject.toml`; `__version__` is derived at runtime via `importlib.metadata`.

### `src/google_ads_mcp/server.py`

```python
"""FastMCP server entry point for google-ads-mcp."""

from fastmcp import FastMCP

mcp: FastMCP = FastMCP("google-ads-mcp")


@mcp.tool
def ping() -> dict[str, bool]:
    """Health check. Returns `{"ok": True}` if the MCP server is reachable.

    Real Google Ads tools land in later issues; this is the bootstrap connectivity probe.
    """
    return {"ok": True}


def main() -> None:
    """Run the MCP server over stdio. Used as the `google-ads-mcp` console script."""
    mcp.run()


if __name__ == "__main__":
    main()
```

### `tests/test_server.py`

```python
"""Smoke tests for the MCP server skeleton."""

from google_ads_mcp.server import ping


def test_ping_returns_ok() -> None:
    assert ping() == {"ok": True}
```

## Safety model

Every mutation tool will ship with `dry_run: bool = False` and at least one guardrail (`max_increase_percent` or `absolute_cap`). Default cap is `max_increase_percent: 50` when both guardrails are omitted. Full documentation in #11. Contract details in `PRD.md` (Design System) and `standards.md`.

## Verification Required at Scaffold Time

These are points I'm not 100% confident about at design time. The implementer should verify each before writing code:

1. **Current FastMCP major version and decorator syntax.** I'm presenting `@mcp.tool` (no parens) and `from fastmcp import FastMCP`. FastMCP's API has shifted between versions (1.x used `@mcp.tool()`; import path was previously `mcp.server.fastmcp` in some flavors). After `uv add fastmcp`, run `python -c "from fastmcp import FastMCP; print(FastMCP.__module__)"` and skim the changelog for the current decorator form. **Prefer reality over this document if they differ.**
2. **`pytest-asyncio` version compatibility.** `asyncio_mode = "auto"` is safe across recent majors but verify with whichever version `uv add --dev pytest-asyncio` pulls.
3. **PEP 639 license expression on hatchling.** `license = "MIT"` + `license-files = ["LICENSE"]` requires a recent hatchling. If the build complains, fall back to the legacy `license = { text = "MIT" }` form.

## Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| FastMCP API drift breaks the snippet above | Medium | Verification step 1 above; small surface area means quick fix |
| `uv init --package` template injects boilerplate we don't want (sample function, type-stub files) | Medium | After `uv init --package`, sweep generated files; delete or replace anything not in this spec |
| PR #16 (`chore/wf-generate`) hasn't merged when this branch lands its first commit | High | Expected. Rebase `feat/issue-1-bootstrap` onto `main` after #16 merges. No conflicting file paths between the two PRs. |
| Author email visible on PyPI metadata is a personal address | Low (cosmetic) | Decide before tagging v0.1.0 (#7) whether to swap for a noreply form |
